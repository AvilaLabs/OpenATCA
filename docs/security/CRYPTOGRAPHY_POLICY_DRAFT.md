## Security boundary and deployment decision

The selected target is a **separate, on-premises crypto and transport gateway process** that communicates with tracker/safety processes over bounded, versioned plain-data messages. Those processes do not link crypto backends, store private keys, or terminate TLS. The gateway separates TLS handling and key-use policy from tracker logic. AWS-LC is the single allowed external cryptographic module dependency, confined to this gateway's transport crate; OS and TLS protocol glue plus HSM/TPM drivers remain separately inventoried, and no second crypto provider is permitted.

Use the **Marvell LS2 HSM Family module, CMVP certificate 5588**, for the offline root, issuer, release-signing, adaptation-approval, and PQ signature keys. Certificate 5588 is Active, FIPS 140-3 overall Level 3, hardware, sunset 2031-11-15. Its tested hardware configurations include `LS2-G-A300-MI-F-B0` and `LS2-O-A050-IB-F-B0`, hardware version `CN9310410-03 C`, Marvell firmware `10.24-0703`, U-Boot `10.24-0702-R01-SB` and `-R02-SB`, and Octeon TX2. HPS-App `10.24-0703` is outside the cryptographic boundary and requires its own assurance; do not count it as validated LS2 cryptography. The approved algorithms include AES-GCM, ECDSA with FIPS 186-5 services, KAS-ECC P-256/P-384, ML-DSA, and ML-KEM. The TLS KDF is specifically TLS v1.2 KDF RFC 7627; the certificate does not list a TLS 1.3 KDF. Therefore LS2 is for durable/signing operations, not TLS 1.3 ephemeral processing. Keep the root offline, separate keys by purpose and authorization role, and require dual control for root and policy changes. The listed tested host/OE is not an on-premises server integration; qualify that physical integration separately.

Evaluate the STMicroelectronics ST33KTPM2X/ST33KTPM2XSPI under **CMVP certificate 5109** for node hardware identity, measured-boot use, and durable node identity/checkpoint key custody. The certificate is Active, FIPS 140-3 overall Level 2, sunset 2030-12-14; the exact certified components are ST33K1M5T revisions C/D with firmware `9.512` / `0x00.09.02.00`, TPM 2.0 revision 1.59, in the specified Level-2 mode. Its listed ECDSA generation/signature services use FIPS 186-4, and it lists LMS signature verification only; it does not list LMS signing or FIPS 186-5 ECDSA signing. Retain identity and checkpoint keys in the TPM as required, but do not admit production checkpoint signing under this certificate until a certified FIPS 186-5-compliant TPM signing service/configuration is selected and documented. Bind exact TPM part, firmware, host and service before production enrollment.

### TLS secret placement

For node-to-node channels, use mutual TLS 1.3 only. The selected crypto-module strategy is **AWS-LC 4 FIPS 4.0.0 `bcm.o`, certificate 5595**, in an isolated on-premises gateway process for ephemeral ECDHE, TLS 1.3 key schedule, traffic keys, record protection, and resumption PSKs. This is a software module at FIPS 140-3 Level 1: transient TLS values are present in gateway process memory and cross its module API. The gateway must admit no competing or fallback crypto provider for these operations. Durable root, issuer, release, adaptation, and device identity keys remain in the LS2 HSM/TPM; do not import those keys into AWS-LC.

Deploy the gateway on an authority-owned on-premises server running Amazon Linux 2023 on a matching AMD EPYC processor. The CMVP selection section below defines the porting and service-admission evidence; the c7a tested configuration is a qualification reference only.

## Selected protocols, algorithms, and signed objects

### mTLS profile

The initial target profile is TLS 1.3 with mutual certificate authentication and exactly these suites:

- `TLS_AES_128_GCM_SHA256` (baseline)
- `TLS_AES_256_GCM_SHA384` (permitted alternative)

Permit only the `secp256r1` and `secp384r1` ECDHE groups. Accept certificate/handshake signatures `ecdsa_secp256r1_sha256` and `ecdsa_secp384r1_sha384`, with certificate public keys on the matching curve. Bind node identity and role to certificate policy and authorize peers separately after chain, validity, revocation, and purpose checks. Reject TLS 1.2, ChaCha20-Poly1305, unknown suites/groups/signatures, and downgrade attempts in this profile. The selected module's approved-service table must cover every cryptographic operation used in its required mode.

This is a conservative AES-GCM/ECDSA profile for an initial deployment. [NIST SP 800-52 Rev. 2](https://csrc.nist.gov/pubs/sp/800/52/r2/final) addresses TLS 1.2 and TLS 1.3 support; a TLS-1.3-only deployment must separately resolve any interoperability requirement for TLS 1.2. Any compatibility need requires a separately versioned profile and written approval.

### Release, adaptation, and checkpoint signatures

For release and adaptation envelopes, require **two independent signatures over the same canonical bytes**: ECDSA P-384 with SHA-384 and ML-DSA-87, produced by separate purpose-bound keys in the LS2 Level 3 HSM. Certificate 5588's approved-service mapping and A6877 validation cover ML-DSA-87 key generation, signing, and verification; bind the exact certified module configuration and approved mode. Both signatures must verify; there is no alternative or silent single-signature fallback. This dual-signature envelope is two signatures over one payload, not a new combined signature algorithm.

1. **`OpenATCA-Release-Manifest-v1`** — covers product/version, source revision, binary digest, target platform, build provenance identity, SBOM digest, schema/profile versions, release sequence, and signing-key ID. This authorizes a release artifact only when a verifier also checks the release trust chain, role, and revocation status.
2. **`OpenATCA-Adaptation-Authorization-v1`** — covers the baseline configuration digest, proposed configuration digest, facility/node scope, permitted operation, activation and expiry, monotonic authorization sequence, reason/change reference, and approver identities. Require two independent signatures: the safety/configuration authority and the operations authority. A valid signature without the required roles and scope is not authorization.
3. **`OpenATCA-Node-Checkpoint-v1`** — covers node identity, checkpoint/log size, previous checkpoint digest, input and state identities, software/release manifest identity, sequence/freshness, and policy version. Keep the node checkpoint key in that node's TPM. Certificate 5109 does not establish the required FIPS 186-5 signing service, so checkpoint signing remains unavailable until the TPM configuration/profile admission gap is resolved; do not relocate this key to the LS2 HSM. Witness countersignatures bind both the peer checkpoint and consistency proof to the witnessing node identity and follow the same TPM key-custody rule.

For every security decision based on these envelopes, the signing/verifying service computes or recomputes the security digest, in the module's approved mode, over the exact canonical bytes covered by the signature. Any digest field carried in an envelope must match that module-computed value. `oa-sha256` digests may appear only as diagnostic or reproducibility identifiers; they must not be signed as a substitute for a validated security digest or presented as making an end-to-end chain FIPS validated. A release signature covers canonical manifest bytes; separately compute and verify the release artifact's security digest over the exact artifact bytes. An adaptation signature covers the canonical proposed configuration and its security digest; after authorization, activate those same verified bytes atomically, recomputing immediately before activation and failing on a changed generation or byte. A checkpoint signature covers the exact canonical checkpoint and consistency-proof bytes. Keep diagnostic IDs distinct and labeled so they cannot be confused with these security digests.

Use separate keys for root certification, issuance, release signing, adaptation approval, node TLS identity, node checkpointing, and any other purpose. Signatures identify use of a key under a trust policy; custody, authorization, and governance remain operational responsibilities. Canonical encoding, explicit domain separation, parser bounds, anti-replay, revocation, and key-rotation rules are required before implementation.

## Key hierarchy and lifecycle

1. **Offline trust root:** generate and keep the root private key within the LS2 Level 3 HSM in its approved mode. Require role separation, dual-control ceremonies, logged key activation, tested backup or explicit non-recoverability, and verified zeroization/destruction. The root signs subordinate authority certificates and is not used for routine artifact or node signing.
2. **Issuing and authorization authorities:** use separate LS2-held keys for release manifests and adaptation authorizations, each with dual signatures. Keep key purpose and activation roles separated. Rotate issuers through authenticated bounded overlap signed by the root.
3. **Node identity and checkpoints:** keep each node's durable identity and checkpoint keys in its TPM, bound to measured platform state. Certificate 5109's FIPS 186-4 ECDSA and LMS-verification-only services do not satisfy the proposed FIPS 186-5 checkpoint-signature profile. Production enrollment/checkpoint signing remains gated on a certified FIPS 186-5-compliant TPM service/configuration; do not move these keys to LS2 or software.
4. **Transport:** use AWS-LC 5595 in the isolated gateway for all TLS 1.3 transient-secret operations after the on-prem OE and TLS binding admission gate passes. A provider/OE/self-test/service failure rejects the handshake and fails closed; no alternative provider is permitted.
5. **Operations:** monitor certificate validity and revocation freshness, protect audit records from key disclosure, maintain offline recovery procedures, and fail closed on invalid HSM mode, self-test failure, missing/revoked peer identity, authorization failure, or provider outage. No software-key fallback or silent downgrade is permitted.

## CMVP selection and deployment rule

NIST CMVP lists AWS-LC 4 dynamic **5595** as Active FIPS 140-3 Security Level 1, sunset 2031-11-18. Its module boundary is AWS-LC FIPS 4.0.0 `bcm.o`, dynamically linked to a user-space application. The tested `c7a.metal` profile is Amazon Linux 2023, AMD EPYC 4th Generation, 128 GiB system memory and 200 GiB EBS. The other tested profiles are c6i.metal / Intel Xeon Platinum 8375C / 192 GiB / 200 GiB EBS and r8g.metal-24xl / Graviton4 / 128 GiB / 200 GiB EBS. Certificate 5595 has no vendor-affirmed OE. The security policy also states that it provides no assurance of minimum security for externally loaded SSPs or SSPs derived from those externally loaded. In this design, the software module does not provide hardware isolation: ephemeral/session values exist in gateway process memory and can cross the module API.

Select AWS-LC 5595 for its approved ECDH, HKDF and AES-GCM services, available unmodified source, and Amazon Linux 2023 reference environment. Deploy it on premises; no cloud service is required. Under the **FIPS 140-3 Management Manual v2.8 (2026-11-20), §7.9**, unchanged Level 1 software may be ported to general-purpose hardware supporting its listed OS or a compatible OS. A user may recompile only when the module's security policy supplies an applicable recompilation procedure, followed unchanged. Source modifications require laboratory review and revalidation. Vendor affirmation requires the vendor's laboratory/security-policy update; a port does not add a tested OE to the certificate. CMVP makes no assurance about operation or generated-key strength on an unlisted OE.

For this project's production admission, require vendor-supported on-premises compatibility and the corresponding security-policy update, rather than relying solely on user affirmation. Record the unmodified module, prescribed build, compiler/linker options, processor, OS, approved services and TLS API binding. If source changes or a different OE need validation, obtain it before admission. This stronger project gate gives a supportable procurement configuration for long-lived authority-owned equipment.

The AWS-LC TLS path must use approved ECDH, KDA-HKDF, SHA-2 and AES-GCM services in approved mode. Its `TLS KDF` service is specifically TLS 1.0–1.2; for TLS 1.3, the binding must map each HKDF stage to the approved KDA-HKDF service and use the documented TLS 1.3 AES-GCM behavior. Bind the TLS engine to the `bcm.o` API, prove every cryptographic operation reaches it, prevent fallback providers, and fail closed on self-test, mode, service-indicator, or identity failure. LS2 remains the Level 3 durable-authority/signature module; ST TPM 5109 remains the candidate for node identity/checkpoint key custody subject to its signature-profile admission gap.

## Post-quantum transition

Release and adaptation envelopes require dual ECDSA P-384/SHA-384 and ML-DSA-87 signatures from the LS2 HSM. NIST's LS2 certificate lists ML-DSA KeyGen, SigGen and SigVer via algorithm certificate A6877; its approved service mapping specifies ML-DSA-87 SigGen/SigVer and key generation parameter sets. Bind the exact LS2 firmware/provider and approved mode to those operations. Keep both signature values independently verifiable over the same canonical message; reject if either is absent or invalid. Node checkpoint keys remain TPM-held and are governed by the separate admission gate above.

Use the standardized TLS 1.3 group **SecP256r1MLKEM768** from [RFC 10024](https://www.rfc-editor.org/rfc/rfc10024.html) for the hybrid key agreement profile. It combines ECDHE P-256 with ML-KEM-768; it does not replace endpoint authentication. Before use, qualify the exact AWS-LC 5595 implementation, validated services and approved mode for both components and the prescribed TLS 1.3 composition. The group is not active merely because it is specified in an RFC.

NIST IR 8547 (October 2026) states that NIST will deprecate quantum-vulnerable public-key cryptography after 2030 and disallow it under NIST standards/guidelines after 2035. It also gives federal high-value/high-impact systems key-establishment migration by 2030-12-31 and digital-signature migration by 2031-12-31; the responsible authority must classify this system before those federal deadlines are treated as applicable requirements. This proposal sets an earlier product gate: qualify hybrid ECDHE+ML-KEM by 2029-06-30 and **reject classical-only TLS handshakes no later than 2029-12-31**. If hybrid support cannot be validated by that date, TLS is unavailable; do not silently retain classical-only key establishment. The project target is to stop generating ECDSA-only release/adaptation signatures before NIST's post-2030 deprecation period, with an authority-approved cutover schedule for the dual-signature profile. NIST's standards disallowance timeline after 2035 is an outside limit, not a migration target.

| Target date | Work | Gate |
|---|---|---|
| 2026-12-31 | Freeze canonical envelopes, key purpose separation, and dual ECDSA P-384 / ML-DSA-87 signatures for release and adaptation authorization. | Exact LS2 cert 5588, firmware, ML-DSA A6877 services and approved mode recorded. |
| 2027-12-31 | Complete gateway/TLS integration design for RFC 10024 `SecP256r1MLKEM768`, module-service mapping, peer identity and certificate profile. | No custom combiner; module and TLS implementation must support the standardized group in validated approved services. |
| 2028-12-31 | Qualify hybrid TLS in a non-operational environment with the exact on-prem AWS-LC OE and full application binding. | Independent protocol review and no fallback provider; record all handshake/signature outcomes. |
| 2029-06-30 | Production readiness gate for hybrid TLS. | Exact approved module/OE integration, certificates and peer interoperation; otherwise prepare service shutdown. |
| 2029-12-31 | Refuse classical-only TLS. | Hybrid group required; if it is unavailable, TLS remains unavailable. |
| 2030-12-31 / 2031-12-31 | Meet any authority-classified high-value/high-impact PQ key-establishment/signature deadlines. | Authority applicability and migration evidence recorded. |

No home-grown combiner or implicit classical fallback is allowed.

## Limits and open questions

The inventory covers source and design. Next, inspect the exact built gateway, deployed OS/provider, module firmware, certificate stores and operational controls during qualification; record the responsible authority’s system categorization and authorization requirements. A module certificate validates neither the TLS protocol engine nor the complete gateway.

The on-premises AWS-LC 5595 path depends on vendor-supported compatible OE and exact TLS API binding. If AWS-LC cannot be ported or affirmed for the target server, use a different reviewed validated module/service with the required TLS 1.3 and PQ operations, or keep TLS unavailable; do not substitute an unvalidated library. The c7a/Amazon Linux configuration is a NIST-tested cloud reference and is not the deployment runtime. LS2 certificate 5588 hardware/firmware must match its tested IDs, and HPS-App is outside the validated boundary. TPM 5109's FIPS 186-5 checkpoint-signature admission gap requires a compatible certified FIPS 186-5 TPM signing configuration/service; node checkpoint keys remain TPM-held while that gate is unresolved.

Before implementation, bind LS2 certificate 5588 to its exact part, hardware/firmware, approved mode, services, PCIe interface and host; bind AWS-LC 5595 to its exact unmodified module build, vendor-affirmed on-prem OE, provider/TLS call path, service indicators, and fail-closed behavior. Resolve TPM 5109's checkpoint-signature profile gap with a certified FIPS 186-5-compliant TPM signing configuration/service without relocating node identity/checkpoint keys. The responsible authority must classify the system for applicable NIST IR 8547/OMB transition deadlines and confirm whether TLS 1.3-only meets [SP 800-52 Rev. 2](https://csrc.nist.gov/pubs/sp/800/52/r2/final) tailoring and compatibility requirements; if TLS 1.2 support is required, define a separate profile and establish its approved module/service mapping. Also specify trust bootstrap, revocation and freshness sources, role authorization, rotation/recovery, canonical encodings, parser limits, audit retention, and operational key custody.
